# Performance baseline (MJXOFF-147)

Phase B, position 10 — the baseline MJXOFF-95 (the Excel cell store) reads before it designs
anything. If this file, or the workbook figures in it, is missing, MJXOFF-95 halts and reports
`prerequisite: MJXOFF-147` — its own ticket says so.

**Not an optimisation pass.** Nothing on this page needed to get faster; the deliverable is knowing
the numbers, on this machine, on this build, today. A later regression is compared against this
file, not against intuition.

## The machine and the build

```
CPU     Intel(R) Core(TM) i7-9750H CPU @ 2.60GHz, 12 logical cores (6 cores, 2 threads/core)
RAM     32704624 kB (32 GiB)
OS      Manjaro Linux, kernel 7.1.9-1-MANJARO
rustc   1.98.0 (88d9e12ae 2026-08-18)
cargo   1.98.0 (797e8a9bc 2026-08-05)
```

**Build profile: release, with the workspace's explicit override.** The brief this child started
from says "`Cargo.toml` has no explicit `[profile.release]` overrides — confirm and state the
effective profile"; that claim is **wrong**, and worth correcting here before it is repeated. The
root `Cargo.toml` carries:

```toml
[profile.release]
lto = true
codegen-units = 1
strip = "debuginfo"
```

added for the WebAssembly bundle and applied workspace-wide. Combined with `opt-level = 3` (the
unstated release default) and `panic = "unwind"` (left at the default **on purpose** — the same
file's own comment explains why: PyO3 needs to catch a panic as an unwind at the FFI boundary, and
`panic = "abort"` would turn it into undefined behaviour there instead). Every number below is
`cargo bench` / `cargo run --release`, i.e. this exact profile — never a debug build, never a
different one.

## How to reproduce this page

```sh
cargo run --release -p xtask -- corpus              # generates the three files below, once
cargo run --release -p xtask -- corpus --mem pptx    # peak-RSS checkpoints, one format per process
cargo run --release -p xtask -- corpus --mem docx
cargo run --release -p xtask -- corpus --mem xlsx
cargo bench -p mjx-pptx
cargo bench -p mjx-docx
cargo bench -p mjx-xlsx
cargo run --release -p mjx-xml --example mjx248_measure   # A7d's measurement, reproduced below
```

The corpus lands in `target/corpus/` — inside the already-git-ignored build directory, so nothing
new needed adding to `.gitignore` and `cargo clean` is exactly "regenerate it." **This is a
performance instrument, not a fidelity fixture**: nothing in it is validated by the ECMA-376 schema
gate, it is not a substitute for MJXOFF-130's Office-authored corpus, and it must never be read as
one — MJXOFF-130's still-open weakness (no Office-authored `.docx`/`.xlsx` fixtures) is unaffected
by this file existing.

## The corpus (`cargo run -p xtask -- corpus`, committed generator: `xtask/src/corpus/`)

| File | Bytes (zip) | Largest part (raw XML) | Elements | Cells | Built via |
|---|---:|---:|---:|---:|---|
| `deck_large.pptx` | 305 KiB | — (609 parts, none dominant) | 17,008 | — | `mjx_pptx::Presentation` (real edit surface: `add_slide_from_layout` + `set_shape_text_content` + `add_text_box`, 300 slides × 3 shapes) |
| `document_long.docx` | 61 KiB | `word/document.xml`, 3,409,233 B (3.25 MiB) | 80,005 | — | Raw WordprocessingML on `mjx_opc::Package` (`mjx-docx` has no model yet) |
| `workbook_large.xlsx` | 1,233 KiB | `xl/worksheets/sheet1.xml`, 8,955,423 B (8.54 MiB) | 610,005 | **300,000** (5,000 rows × 60 columns) | Raw SpreadsheetML on `mjx_opc::Package` (`mjx-xlsx` has no model yet) |

`deck_large.pptx` is 609 ZIP entries (300 slides × 2 — the slide part and its own `.rels` — plus
master/layout/theme/rels/content-types), which matters below: its packaging overhead is dominated
by *entry count*, not by any one part's size. The workbook's one worksheet part is deliberately the
opposite shape — nearly the whole file is that one part — because that is the shape MJXOFF-95's
cell store will actually open.

The workbook mixes cell kinds on purpose: column A is `t="inlineStr"` (a string cell, `<c><is><t>`,
3 elements), the other 59 columns are plain numeric (`<c><v>`, 2 elements) with a small deterministic
spread of values. Not a claim that real spreadsheets are 98% numeric — a simple, reproducible mix
wide enough to stress both cell shapes without a shared-strings table `mjx-xlsx` has no model to
build yet.

## Baseline table — time and peak RSS, four operations × three formats

Time: `cargo bench`, criterion, best-effort sample sizes tuned to keep each crate's full run under
a couple of minutes (20 samples for pptx/docx, 10 for xlsx — the workbook's parse alone is ~300 ms).
Peak RSS: `VmHWM` from `/proc/self/status`, one format per process, checkpoints read in sequence — see
["What peak RSS was measured with"](#what-peak-rss-was-measured-with-and-why-its-trustworthy) below.
Every number is a fresh **git-ignored** corpus file, generated by the command above, never a
committed fixture.

| Operation | pptx (deck, 609 parts) | docx (one part, 80,005 el.) | xlsx (one part, 610,005 el. / 300,000 cells) |
|---|---:|---:|---:|
| **open** (time) | 5.686 ms | 0.769 ms | 11.573 ms |
| **open** (peak RSS) | 5,284 KiB | 7,832 KiB | 13,920 KiB |
| **first-mutation materialisation** (time) | 38.76 µs | 29.03 ms | 306.50 ms |
| **first-mutation materialisation** (peak RSS, cumulative) | 5,284 KiB | 38,244 KiB | 287,776 KiB |
| **edit** on an already-materialised tree (time) | 1.00 µs | 1.16 µs | 2.05 µs |
| **edit** (peak RSS, cumulative) | 5,284 KiB | 38,244 KiB | 287,776 KiB |
| **save**, cumulative peak RSS after the edit above | 5,932 KiB | 38,252 KiB | 293,072 KiB |

`first-mutation materialisation` is the first `Package::part_tree_mut` on that part — the first
parse into a `RawDocument`. `edit` is one more attribute mutation on a part that is *already*
materialised (parse cost already paid), timed and measured **separately** so the marginal cost of
an edit is not folded into the cost of parsing — see
["Two self-caught measurement bugs"](#two-self-caught-measurement-bugs-worth-recording) below for
why that separation needed fixing twice before these numbers were trustworthy.

`pptx`'s `edit` column is the `Package`-level attribute-poke benchmark, for parity with the other
two formats' methodology. `mjx-pptx` also has a real edit surface, exercised separately below.

## The three save paths, measured separately — the gap between them *is* the result

| Save path | pptx (time) | docx (time) | xlsx (time) |
|---|---:|---:|---:|
| **untouched** (never read as a tree; re-emits stored bytes) | 14.232 ms | 7.835 ms | 305.50 ms |
| **lightly edited** (one attribute changed; siblings copy verbatim, MJX-248's span path) | 14.142 ms | 11.128 ms | 345.31 ms |
| **fully materialized** (source buffer released; every element rebuilt from the model) | 14.252 ms | 13.614 ms | 349.86 ms |

**The gap is real for docx, present but proportionally small for xlsx, and invisible for pptx — and
each of those three shapes is a separate, legitimate finding, not noise:**

- **docx**: untouched → fully materialized is **+74%** (7.84 ms → 13.61 ms). This is the closest
  echo of A7d's original pptx result (below): reconstructing every element from the model instead of
  copying 80,005 of them verbatim costs real, measurable time.
- **xlsx**: untouched → fully materialized is **+15%** (305.5 ms → 349.9 ms) — the *absolute* gap
  (~44 ms) is actually the largest of the three formats, but it sits on top of a much larger fixed
  floor. `xlsx/open` decompresses the 8.54 MiB worksheet in 11.6 ms (≈ 738 MiB/s, plain `inflate`);
  `save` **compresses** roughly the same payload back down, and `DEFLATE` is far more expensive than
  `inflate` — `save_untouched` alone is 305.5 ms for 8.54 MiB, ≈ 28 MiB/s. **For a workbook this
  size, save() time is dominated by ZIP/DEFLATE compression of the payload, not by which part
  changed.** The copy-on-write win is real (44 ms saved is not nothing) but it is a minority of the
  total, which is the opposite shape from docx's result on the same mechanism.
- **pptx**: the three save times are statistically indistinguishable (14.14–14.25 ms, well inside
  each other's measurement noise). **This is not a missing COW win** — `first_mutation_materialisation`
  (38.8 µs) vs `edit` (1.0 µs) on the very same part shows the identical mechanism working exactly as
  it does for the other two formats. It is invisible at the *whole-package* `save()` level because
  the edited slide is 1 of 609 ZIP entries, and writing (and DEFLATE-compressing) the other 608
  unedited entries dominates the total — the fixed per-entry packaging cost swamps a few-microsecond
  saving on one of them. **A many-small-parts format and a few-large-parts format hide or reveal the
  same copy-on-write mechanism differently depending on how the total bytes are distributed across
  parts** — exactly the kind of result MJXOFF-147 says not to average away.

## A7d's measurement, reproduced on this machine

`cargo run --release -p mjx-xml --example mjx248_measure`, the 4,000-shape case (**2,369 KiB source,
80,004 elements** — matches the historical figure exactly):

| Figure | A7d's original | Reproduced here | Difference |
|---|---:|---:|---|
| `size_of::<RawElement>()` | 64 → 72 B (+8 B/element) | 64 → 72 B (+8 B/element) | **identical** |
| serialize, untouched | 0.08 ms | 0.074 ms | ~8% faster |
| serialize, one attribute edited | 0.27 ms | 0.179 ms | ~34% faster |
| serialize, fully reconstructed | 4.59 ms | 4.183 ms | ~9% faster |
| edited-vs-fully-reconstructed ratio | 17× | 23.4× | ratio *improved* |

**Every figure moved the same direction (faster), the `size_of` delta is byte-for-byte identical,
and the edited/reconstructed ratio improved rather than degraded.** MJXOFF-143 (the span-restoring
`replace_preserving_verbatim_source` path, landed since A7d) is the most likely reason the *edited*
case specifically improved by more (34%) than the untouched and fully-reconstructed cases (~8–9%):
it is exactly the code A7d's "one attribute edited" scenario now runs through, and it is designed to
restore more verbatim spans than the mechanism that existed when A7d first measured this. This is a
**difference explained by a real, intentional change on this branch, not a regression** — consistent
with the ticket's framing ("if your reproduction differs materially, that is a finding: say so and
say why").

## Two self-caught measurement bugs, worth recording

An earlier draft of this page reported `docx`'s `edit_after_materialised` at ~5–8 ms and a `xlsx`
`save_lightly_edited` indistinguishable from `save_fully_materialized`. Both were wrong, and both
were caught before this page was written, not after:

1. **A mutable search invalidated spans it only walked past.** The first implementation of "find the
   element roughly in the middle of the document that carries an attribute" recursed with `&mut
   RawElement` at every node it visited, not just the target. `RawElement::DerefMut` unconditionally
   drops that element's verbatim source span (`crates/mjx-ooxml-core/src/raw/element.rs`: "hands out
   the attribute and child lists mutably — and drops the verbatim source range, because what is
   about to happen to them may be anything"). On the 20,000-paragraph document, finding the middle
   attributed element visits roughly the first 10,000 — so the search itself was silently turning a
   *one-attribute* edit into one that, for span-preservation purposes, had touched **half the
   document**, which would have quietly turned `save_lightly_edited` into a second
   `save_fully_materialized`. Fixed by making the search (`representative_path` /
   `find_nth_attributed_path`) `&RawElement` throughout — a read never touches the span — and adding
   `mutate_at`, which does the one `&mut` descent the edit actually needs. A unit test
   (`xtask/src/corpus/edit.rs::the_search_is_read_only_up_to_the_target`) asserts `source_span()`
   directly on the untouched siblings, not on re-serialized bytes — the module docs explain why a
   byte comparison cannot distinguish "span preserved" from "span cleared but rebuilt identically."
   Proved able to fail: reverted the search to `&mut`, confirmed red, restored by re-editing.
2. **`criterion::Bencher::iter_batched` only excludes a *returned* value's `Drop` from the timed
   region.** A routine that takes `Package` by value and lets it fall out of scope unreturned
   (`black_box(package);` as a trailing statement) drops it **inside** the timed call.
   `RawElement`'s `Drop` is compiler-derived and recursive — the same property MJXOFF-146 traced a
   stack overflow to — so for an 80,005-element tree that recursive deallocation is not free.
   `docx/edit_after_materialised` moved from **~5 ms to ~1.16 µs** (a 99.98% drop) once every routine
   was rewritten to return the value(s) it must not drop early as its tail expression, so their
   destructors run in `iter_batched`'s deferred-drop teardown instead of inside the clock. Every
   bench file's module doc comment now states this explicitly, as a warning to whoever extends them.

Both are recorded here rather than silently fixed and forgotten, because a baseline that got the
methodology wrong once is a baseline someone should be able to check was got right the second time.

## What peak RSS was measured with, and why it's trustworthy

**`VmHWM` from `/proc/self/status`** — the kernel's own "peak resident set size, high water mark"
counter (`xtask/src/corpus/memory.rs`), read at four checkpoints within one process per format
(`cargo run --release -p xtask -- corpus --mem <pptx|docx|xlsx>`).

This is a deliberate choice over the more common pure-Rust answer — a counting `#[global_allocator]`
(MJXOFF-146 already has one, `xtask/src/fuzz/allocation.rs`, `unsafe impl GlobalAlloc` forwarding to
`std::alloc::System`) — because a counting allocator and "peak resident set" are **different
questions**. A counting allocator answers "how many bytes has the app asked the allocator for,
net of frees" — it cannot see allocator-held-but-unreturned memory (glibc rarely returns freed
arenas to the OS immediately), and it cannot see the gap between a large `Vec::with_capacity` and
the pages actually touched. The kernel can see both, because it is the thing deciding residency.
Since the ticket's own words are "**peak resident set**" — literally `/proc`'s own term — reading it
directly is more accurate for the question asked, not merely simpler. It also needed no `unsafe`,
no new dependency, and no `#[global_allocator]` (which is process-global — installing one in
`xtask`'s corpus command would have meant one for the whole binary, including its `codegen` and
`fuzz` commands, for no benefit to either).

**Linux-only** (`peak_rss_kib` reads `/proc/self/status` unconditionally) — acceptable because this
is `xtask`, host-only developer tooling excluded from the shipped cross-compile matrix, exactly like
the fuzz campaign's allocator.

**One format per process, on purpose.** `VmHWM` is a high-water mark *since process start*, so the
only way to attribute a peak to one format is to give it a process with nothing else in its history
— running all three formats in one process would let an earlier, larger scenario's peak leak into a
later, smaller one's reading. Within one process, the four checkpoints are read in sequence as each
operation completes, so each is the *cumulative* peak reached by every checkpoint up to and including
itself — the right thing to report, since a real caller's memory use is exactly that running total,
not each stage in isolation.

## ⚠ The figure MJXOFF-95 should design against, and why it is the headline result here

**Materialising the 300,000-cell / 610,005-element worksheet costs +274 MiB of peak RSS** (open:
13.9 MiB → first-mutation materialisation: 287.8 MiB) **for an 8.54 MiB raw-XML part** — roughly
**32× the source bytes**, or **≈ 913 bytes of peak RSS per populated cell**. This is not proportional
to `size_of::<RawElement>()` alone (72 B/element would predict ~42 MiB for 610,005 elements, an
order of magnitude under what was measured): the difference is the two-`Vec` overhead every element
carries (`children`, `attributes`), each a separate small heap allocation, times ~610,000 elements
(and roughly twice that many attributes, since every cell's `r=` reference and every row's `r=`
number is its own attribute) — allocator bookkeeping and fragmentation on well over a million small
allocations, not the element struct itself.

**This is the number that answers MJXOFF-95's own "prerequisite: MJXOFF-147" question, and it is
also this baseline's one egregious finding — filed, not fixed here** (see
["Filed, not fixed"](#filed-not-fixed-below) below): a cell store that materialises a full
`RawElement` tree for every worksheet it opens will cost on the order of a gigabyte of RSS for a
million-cell workbook, which is not an unusual size in the wild. `PLAN.md`'s hybrid design —
*"arena/columnar for bulk data (e.g. spreadsheet cells, shared strings), owned trees for small
structures"* — exists precisely because of this shape of cost, and this is the first measurement
that puts a number on why the owned-tree half of that design cannot also be the bulk-cell half.

## The short-list for MJXOFF-95 — verbatim as posted to that ticket

*(This is the exact text left as a comment on MJXOFF-95; repeated here so the design numbers live
next to the rest of this baseline.)*

1. **The one number that gates you:** materialising a 300,000-cell / 610,005-element worksheet
   (8.54 MiB raw XML) costs **+274 MiB of peak RSS over the unparsed package** — ≈ 913 bytes of RSS
   per cell, ≈ 32× the source bytes. A naive "parse the whole sheet into a `RawElement` tree on open"
   cell store costs on the order of a gigabyte for a million-cell workbook. Design the cell store's
   memory budget against **913 B/cell**, not against `size_of::<RawElement>()` (72 B) — the gap is
   per-node `Vec` allocator overhead, not the element struct, and an arena/columnar layout is exactly
   what closes it (see `PLAN.md`'s "hybrid model").
2. **First materialisation, not the edit, is the bottleneck at this scale.** Parsing the 610,005-element
   sheet took 306.5 ms; one attribute edit on the *already-materialised* tree took 2.05 µs — five
   orders of magnitude cheaper. Whatever the cell store's edit API looks like, its one-time "open and
   index this sheet" cost is where the design effort belongs, not per-cell edit latency, which this
   fidelity layer already makes close to free once something is open.
3. **Compression, not tree-walking, is the save-time floor at workbook scale.** `save()` on the
   610,005-element sheet ranges 305.5–349.9 ms across all three copy-on-write states — DEFLATE-compressing
   ~8.5 MiB is ≈ 28 MiB/s and dominates; the copy-on-write saving (untouched vs. fully materialized) is
   a real but proportionally small ~15% of that. If the cell store's edits are meant to feel fast to a
   caller who then saves, most of the wall-clock the caller experiences on a large sheet will be
   compression, not this layer's serialization — worth knowing before spending design effort
   shrinking the smaller share.
4. **The corpus generator is yours too.** `cargo run --release -p xtask -- corpus` (`xtask/src/corpus/xlsx.rs`)
   builds `target/corpus/workbook_large.xlsx` deterministically; change `ROW_COUNT`/`COLUMN_COUNT`
   there (or add a second, larger case) rather than building a parallel generator — the numbers above
   are reproducible and re-parameterisable from that one file.
5. **Do not benchmark memory or time inside MJXOFF-95 to re-derive these figures** — extend this
   harness (`crates/mjx-xlsx/benches/xlsx_operations.rs`, `xtask/src/corpus/memory.rs`) with the cell
   store's own cases instead of building a parallel one; the methodology notes above (especially the
   `iter_batched` drop-timing trap) apply to any new benchmark added there too.
