# The fidelity oracle — what it proves, what it refuses to claim, and the one thing only you can do

`07-the-reference-pack.md` is addressed to a person with Microsoft Office in front of them. **This
page is addressed to a person with a browser in front of them**, and it asks for something smaller
and more often: *look at five pictures and say whether they are right.*

That sounds like a formality. It is the single thing that stops this whole harness being circular,
and the reason is worth one paragraph before anything else.

---

## 1 · The trap this crate exists to answer

**A golden image generated by the code under test always matches the code under test.**

Regenerate-and-compare is green by construction. If the images in
`crates/mjx-render-oracle/baselines/` were produced by the renderer and then compared against the
renderer, a suite over them would pass on the day the renderer started drawing every shape upside
down — because it would have written the upside-down image into the baseline first. Nothing
mechanical can break that circle. Only a person looking can.

So the crate is built around three refusals, and none of them is a matter of policy:

1. **A baseline with no approval record fails**, rather than passing. Not warns, not skips.
2. **Regeneration is explicit and cannot happen implicitly.**
   `Baselines::regenerate` takes a `RegenerationIntent`, and the only way to get one is to set
   `MJX_ORACLE_REGENERATE=1`. There is no other constructor, so a check path cannot make one by
   accident.
3. **Regeneration removes the approval it overwrites**, before it writes anything. A path that kept
   the approval would ratify exactly the regression it exists to catch.

And an approval binds **the bytes, not the name**: it records a SHA-256 per artefact, which
`sha256sum` reproduces, so a record is auditable by the person whose approval it claims.

---

## 2 · The honest state today: nobody has looked

Every baseline this repository ships is stamped `approver = generator`. That is a **real** approval
record — the digest binding is live, so a silent regeneration is still caught — and it is
**not a human review**. `cargo run -p mjx-render-oracle -- list` says so for each one, the gallery
says so at the top of its page, and the manifest says `"reviewed": false`.

An agent cannot manufacture a person's approval, and stamping one with a human's name would be worse
than having no approval machinery at all. So the machinery records what is true and waits.

**This section stops being true the first time you run the five commands in §4.**

---

## 3 · What the oracle proves, and what it will not claim

**What it proves today:**

* The rendering path — `FragmentTree → DisplayList → pixels` — still produces what it produced when
  a baseline was taken, and **which of the three stages moved** when it does not. A wrapped line
  surfaces as a named line of a fragment snapshot, not as a grey smear.
* Every plate draws the document's own geometry: `DrawReport::placeholders` is zero, asserted,
  beside a non-zero draw count — because zero placeholders is also true of a page that drew nothing.
* The PDF **layout tier** works, on our own exports, before the Windows sitting: two documents' word
  boxes are compared and a one-word displacement is *named*.
* The PDF **pixel tier** rasterises both sides with one rasteriser at one stated DPI, which is the
  only construction in which "pixel perfect against PowerPoint" is a coherent phrase.

**What it will not claim:**

* That any page matches PowerPoint. Not one. Parity needs an *authoritative* reference, and the only
  authoritative provider is an Office export; there are none. `parity` is `false` on every plate, by
  construction rather than by policy.
* That anybody has looked at the images. See §2.

## 4 · What to do, and it takes five minutes

```sh
cargo run -p mjx-render-oracle -- gallery
```

That writes `target/oracle-gallery/index.html` — one self-contained page, no script, no network —
with the five plates, what each is for, and what the oracle can and cannot say about it. Open it.

Then, for each plate you are willing to vouch for:

```sh
MJX_ORACLE_APPROVED_BY='Your Name' \
  cargo run -p mjx-render-oracle -- approve solid-panels "the fills are where the fragments put them"
```

The five plates, and what to look for in each:

| Plate | What it should be |
|---|---|
| `solid-panels` | three blue rectangles stepping down and to the right, on white, no outlines |
| `stroked-frames` | the same three, each with a dark two-point outline |
| `preset-star` | one five-pointed star, filled blue, outlined dark, centred and not clipped |
| `gradient-panel` | one panel, blue on the left running through white to near-black on the right |
| `nested-groups` | a grey clipped band, a half-opaque blue box inside it, a gold outlined box inside that — **three distinguishable colours**, which is the point |

The last one is worth a sentence. Its innermost box was originally drawn in the same ink as the
group containing it, so it was *invisible*: a change to it would have moved no pixel and the
specimen would have proved that the code ran and nothing about what it did. If you can see three
colours there, the fixture is doing its job.

**Say no when it is wrong.** An approval you did not mean is worse than no approval, because the
whole point of the record is that somebody meant it.

## 5 · When a baseline legitimately changes

A renderer improvement moves an image, and that is normal. The sequence is:

```sh
MJX_ORACLE_REGENERATE=1 cargo run -p mjx-render-oracle -- regenerate preset-star
cargo run -p mjx-render-oracle -- gallery      # look at it
MJX_ORACLE_APPROVED_BY='Your Name' \
  cargo run -p mjx-render-oracle -- approve preset-star "the star's inner radius is right now"
```

Between the first and the third commands the baseline is **unapproved**, and `cargo test` is red.
That is deliberate: the window in which nobody has looked at a new image is a window the build should
be complaining about.

`approve` refuses outright under continuous integration, where there is nobody to look.

## 6 · The three tiers, and why a failure names a stage

| Tier | Subject | Catches | Needs a painter? |
|---|---|---|---|
| 1 | `FragmentTree` snapshot | layout: where things are, how they nest, what handles they name | no |
| 2 | `DisplayList` snapshot | scene building: which commands, in what order, with what paints | no |
| 3 | rendered pixels | painting: tessellation, blending, effects, the rasteriser | yes — the software one, which needs no GPU |

The **first** tier to differ is the one that caused it, because every later tier is downstream. So a
failure reports `Layout`, `SceneBuilding` or `Painting` and tells you which crate to open, rather
than reporting that the picture changed.

A recolour is the case that proves the tiers are independent rather than three views of one
comparison: a fragment tree carries a `DecorationRef` — a bare number — and never a colour, so tier
one *cannot* see a recolour, and tiers two and three can.

## 7 · The two traps, pointing in opposite directions

Both are enforced by `ReferenceProvider`, which the reference pack shares with this crate.

* **A provisional baseline read as parity.** If baselines were approved against LibreOffice now and
  quietly kept when PowerPoint arrives, LibreOffice's quirks would be ratified into the ledger —
  strictly worse than having no reference, because it *looks* like parity.
* **A reference defect read as our defect.** LibreOffice's PDF export does not reproduce gradients or
  shades. A pixel difference there is the reference's fault, and **nothing in a pixel diff says which
  way round it is** — so an agent could spend a whole child "fixing" correct code until it matched a
  bad export.

The answer to both is that the exclusion belongs to the **provider** and not to the fixture, so it
lifts by itself the day an Office export arrives; that an excluded result is *not evidence* —
neither a pass nor a failure; and that the reason is printed rather than left as a gap.

**The layout tier is never excluded.** A word's bounding box says nothing about how the shape behind
it is filled, so `pdftotext -bbox-layout` stays fully meaningful on exactly the files whose pixel
tier is compromised. Do not disable a whole fixture when only its pixel tier is affected.

---

## 8 · The document fixtures, and the empty column

The gallery lists every package in `mjx-fixtures` — derived from the corpus, never from a list —
and none of them has a plate. **No format renders yet**: a `.pptx` becomes a fragment tree from R14
onward. The rows exist so that the day one does, every fixture is already in the gallery rather than
waiting to be remembered.

A row with no image and no reason would look like a failure. Each carries the reason instead.
